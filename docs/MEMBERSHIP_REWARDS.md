**KI は「AI 競馬予想 ＋ 長期会員クラブ」である。**

## 3. 制度の全体像（確定した構造）

新設する制度は次の 6 本。**構造・数値ともに確定済み**（TBD-1〜TBD-10 → §7.1 / §7.6 / §7.7）。
景品の品目（§7.8）と発送先住所（§7.9）も **2026-09-07 に確定**した。
残る未確定は **包装資材費・景品価額（TBD-13）**と、**景品の仕入れの実行**だけである（§7.5）。

| # | 制度 | 確定した内容 |
|---|---|---|
| M-1 | **継続価格ロック** | 契約中は、その会員が**加入した時点の契約価格を維持できる**。将来の新規価格を変更できるよう、**契約時価格を会員単位で保持する** |
| M-2 | **継続プレゼント** | 会員継続期間に応じて**実物**のプレゼントを受け取れる |
| M-3 | **選べるプレゼント** | 条件達成時に**複数候補から選べる**。景品カタログは**設定・データ駆動**で将来変更できる |
| M-4 | **長期会員優遇** | 長期会員ほどリワード・交換待遇を優遇できる構造を持つ |
| M-5 | **会員ランク** | **Bronze / Silver / Gold / Platinum** の 4 段階 |
| M-6 | **継続記念品** | 長期継続の節目で、通常のポイント交換とは**別枠**の記念特典を提供できる |

### 3.1 M-1 継続価格ロック

- 契約時の請求額（Stripe Price の実額）を **会員レコードに保存**する。
- 保存するのは「新規価格を将来変更しても、契約中の会員の請求額を維持する」ためである。
- 🔴 **Stripe の Price を後から書き換えて既存会員の請求額を変えない。**
  新規価格は **新しい Price を作って切り替える**（既存サブスクは旧 Price のまま）。
  したがってロックの実効は Stripe 側にあり、KI 側の保存値は **表示と監査のための写し**である。
- 🟢 **確定（2026-09-01・§7.1 TBD-8）**: 解約後の再加入は **90 日以内なら旧価格を復活**し、
  超えたら新価格。`priceLock.js` の `REENTRY_GRACE_DAYS` に実装済み。

### 3.2 M-5 会員ランク（Bronze / Silver / Gold / Platinum）

🔴 **ランク差は「リワード・プレゼント・長期待遇」に限定する。**

| 差を付けてよいもの | 差を付けてはいけないもの |
|---|---|
| リワードの積み上がり方 | ❌ **予想の精度** |
| プレゼントの選択肢・交換待遇 | ❌ **買い目の内容・点数** |
| 継続記念品 | ❌ **有料情報の質・公開範囲** |
| — | ❌ **tier（`free` / `light` / `premium`）の権限** |

- ランクは `premium` の**継続月数**から決まる（構造）。昇格月数は
  **Bronze 0 / Silver 3 / Gold 12 / Platinum 24 か月**（§7.1 TBD-2・確定）。
- ランクは **entitlement に影響しない**。`canSeeMarks` / `canSeeBetting` はランクを受け取らない。

### 3.3 KI リワード

- **Premium を継続することで自動的に積み上がる。**
- ❌ ログイン報酬・育成・クリック報酬ではない。
- UI では「積み上がり」を感じられるようにする。ただし次を厳守する。

🔴 **表現規約（違反はテストで落とす）**

| 使ってよい | 使ってはいけない |
|---|---|
| KI リワード残高 | ❌ 貯金 / 預金 / 積立金 |
| 今月の積み上げ | ❌ 現金 / キャッシュ / 円換算 |
| 次のプレゼントまであと◯◯ | ❌ 換金 / 出金 / 払い戻し（リワード文脈で） |
| ポイント | ❌ 残高（円）/ 口座 |

- 🔴 **リワードは現金・預金ではない。換金可能な残高として実装しない。**
  金額（円）への換算表示を行わない。出金・送金・譲渡の経路を作らない。

## 4. 申込ページ（`/pricing`）の二本柱

`/pricing` は「予想機能一覧＋価格」だけではなく、**二本柱**にする。

```
柱1: 予想サービスの価値      （既存のマトリクス・月額プラン）
柱2: 続けるほど会員価値が積み上がる（本制度）
```

柱2 に出してよい訴求（**確定しているものだけ**）:

- 月額 ¥3,980
- KI リワードが毎月積み上がる（**100 pt / 月**）
- Bronze → Silver → Gold → Platinum（**0 / 3 / 12 / 24 か月**）
- 選べるプレゼント（**600 pt / 1,200 pt** の 2 段階）
- 長期継続記念品（**12 か月・24 か月**）
- 継続価格ロック
- 次の特典までの進捗

🔴 **UI に出してよい数値は §7.1 の確定値だけ。**
**未確定値（包装資材費と景品価額 TBD-13）は出さない。**
🔴 **景品の品目（§7.8）は `/pricing` にも規約にも書かない。**
品目はカタログのデータで変わりうるものであり、規約や訴求へ固定して書くと
後から狭める変更が不利益変更になる。品目を出すのは **`/mypage` の申込欄だけ**
（カタログのデータから描画する）。
（TBD-9 / TBD-10 は 2026-09-01 に確定したが（§7.6 / §7.7）、**内部の判定ルールであって
UI に数値として出すものではない**。UI に出してよいのは従来どおり上記の訴求だけ。）
架空値・例示値・「たとえば〜」も出さない。未確定箇所は **「準備中」** と表示する。

### 6.1 fail-closed の定義（本制度）

| 状況 | 挙動 |
|---|---|
| 継続月数が不明（起点が未保存＝`MembershipStartedAt` が空／支払い済み期間を数えられない） | ランクを**返さない**（`monthsKnown: false`）。Bronze へ倒さない |
| 昇格月数の設定が壊れている（順序逆転・欠落など） | ランクを**返さない**。既定値へ黙って戻さない |
| 台帳が読めない | 残高・積み上げを**返さない**（`pending`）。0 pt と言い切らない |
| 記念品の月（12 / 24 か月） | 通常交換の候補を**出さない**（`blockedByMilestone`。§7.4） |
| 解約後 90 日を過ぎている | ポイントは **失効**（`expired`）。残高を表示しない |
| 景品カタログが `draft` / 空 | 交換可能プレゼントを**出さない**（品目が確定していても、配れないうちは出さない）|
| 同じ交換ライン／節目に候補が複数ある | **すべて**返す。🔴 こちらで 1 つに絞らない（絞ると自動割当になる。§7.8）|
| 景品の価額（`valueYen`）が未設定 | ¥796 の検査を**素通しにするだけ**。推測した価額を**当てはめない**（TBD-13）|
| 交換履歴（`RewardRedemptions`）が読めない | 交換を**受け付けない**（503）。記念品の二重申込を見逃さないため |
| 発送キューへ積めなかった | ポイントを**引かない**（503）。ポイントだけ減る状態を作らない（§7.9・G-27）|
| 減算が失敗した | `requested` のまま残す。**`approved` にしない**＝発送対象にならない。再送で回復する |
| 回復時に残高が足りない | `approved` にしない。`requested` のまま残す（運用者が取り消せる）|
| 住所の必須 3 項目が欠けている | 交換を**受け付けない**。空欄のまま発送依頼を作らない |
| 契約価格が未保存 | 「準備中」。¥3,980 を**推測で当てはめない** |
| 永続化が無効 / 未設定 | `unavailable`。**「達成しました」と表示しない** |
| 交換履歴が読めない | 「準備中」。🔴 **「まだ受け取られた特典はありません」と言い切らない**（受け取り済みの特典を「無い」と伝えることになる）。0 件と断定してよいのは台帳が読めたときだけ |

### 7.2 なぜ ¥796 なのか（保守ラインの根拠）

総付景品（購入者全員に提供する景品類）は、**取引価額が 1,000 円以上なら取引価額の 10 分の 2** が上限。
月額 ¥3,980 に対して **¥796**。

- これは「取引価額＝月額」という **いちばん厳しい読み方**での上限である。
  年額で見ればさらに余裕があるため、**¥796 に収めておけばどちらの読み方でも収まる**。
- したがって **取引価額の解釈を確定させる必要がない**（§8 の確認を待たずに運用できる）。
- 🔴 **¥796 を超える景品を出す判断をした時点で、取引価額の確認が必要になる。**
- 送料は景品価額に含めない整理が一般的だが、**含めて計算しても収まる水準**にしておくこと。

### 7.3 全員同一条件を保つ（総付を維持する）

- **抽選・くじ・先着などの偶然性を入れない。** 入れると一般懸賞になり別の上限が適用される。
- 「選べるプレゼント」は **同じ条件を満たした人に同じ候補を提示して選ばせるだけ**にする。
- 上位ランクの優遇は **候補の幅（`minRank`）**で行い、**必要ポイントの割引では行わない**
  （同じ景品を人により違う条件で出すと説明が複雑になるため）。

### 7.4 記念品と通常交換を同月に重ねない

12 か月目・24 か月目は記念品の月とし、**その月は通常のポイント交換を受け付けない**。

- 目的は 1 か月あたりの景品類を ¥796 の枠に収めること（記念品と交換品の合算を避ける）。
- 実装: `catalog.js` の `isMilestoneMonth(months)` が真の月は
  `exchangeView` が `blockedByMilestone` を返し、交換候補を出さない。

### 7.6 TBD-9 継続月数の起点 ＝ **支払い成功日**

| 経路 | 起点 |
|---|---|
| Stripe 月額 | **初回の支払い成功**（`invoice.payment_succeeded` / Checkout 完了時の支払い） |
| 銀行振込 年払い | **入金確認日**（`Status` を active にして入金確認メールを送った日）|

Stripe の実装（2026-09-10 接続）:

- `stripe-webhook.js` の `invoice.payment_succeeded` で、**台帳へ積んだあと**に
  `store.saveMembershipStart(email, <paid_at>)` を呼ぶ。
- 起点は **`status_transitions.paid_at`**（＝付与に使う `occurredAtMs` と同じ値）。
  🔴 **webhook の受信時刻で代用しない**（再送・遅延で起点がずれる）。

- 🔴 **呼ぶのは「Stripe 側で初回請求と確定できる invoice」だけ。**
  判定は **`invoice.billing_reason === 'subscription_create'`**
  （`isFirstBillingInvoice()`）。

  | `billing_reason` | 意味（stripe 22.6.0 の API 契約）| 起点を書くか |
  |---|---|---|
  | `subscription_create` | **A new subscription was created**（初回請求）| ✅ **書く** |
  | `subscription_cycle` | A subscription advanced into a new period（更新）| ❌ |
  | `subscription_update` / `subscription_threshold` | 変更・閾値 | ❌ |
  | `subscription` | 2018 年 5 月以前の旧値。**初回と更新を区別しない** | ❌ |
  | `manual` / `quote_accept` / `upcoming` / その他 | サブスクの初回ではない | ❌ |
  | 欠落 / `null` / 未知の将来値 | 判定できない | ❌ |

  🔴 **`MembershipStartedAt` が空だから書く、にしてはいけない。**
  起点が空の会員へ更新請求が来たとき、その支払日を入れると
  **継続月数が実際より短くなる**（長く続けている人が新規扱いになる）。
  🔴 **判定できないものは書かない。** 推測で初回とみなさない。
  型に未知の文字列が含まれる＝将来値が増えうるため、
  **除外リスト方式にしない**（未知が初回として通る）。
  判定できない請求では **付与（accrual）だけ行い、起点は skip する**
  （`FAILED` にして再送させない）。

- 🔴 **二重の防御。** 仮に初回と判定されても、store 側が既存値を見て
  `ALREADY` を返し **PATCH を投げない**。
  ここを上書きすると、長く続けている会員の継続月数が毎月 0 に戻る。
- 前提（**`amount_paid > 0` / 間隔既知 / `paid_at` あり**）が欠けた請求は
  その手前で return しているので、**支払いが成立していない請求で起点は入らない**。
- 書き込みに失敗したら **event を processed にしない**（Stripe の再送で復旧させる）。
  再送しても既存値があれば `ALREADY` なので二重に動かない。

🔴 **2026-09-10 まで、この書き込みはどの Stripe 経路にも存在しなかった**
（webhook は `saveContractPrice` と `appendEntry` しか呼んでいなかった）。
表示は台帳から継続月数を出すため壊れていなかったが、
**台帳が読めないときのフォールバックが空のまま**だった。
QA の Test Mode E2E（経路 A）で実測して判明した。

銀行振込の実装（2026-09-01 接続）:

- `send-payment-confirmation-auto.js`（入金確認メール）の **最後**で会員継続制度へ反映する。
  🔴 メール送信・`AccessEnabled` の更新が済んだ**あと**に、**別リクエストで**行う。
- 期間は `plan_type` から決める（`bankTransfer.js` の `BANK_PLAN_TERM_MONTHS`）。
  **`calculateExpirationDate` と同じ規則**にすること（有効期限と継続月数がずれるため。テストで固定）。
  - `yearly` → **12 か月・1,200 pt** / `light`・`monthly-*` → 1 か月・100 pt
  - 🔴 `lifetime`・未知・未設定 → **付与しない**（月額へ丸めない）
- 冪等キーは **`bank:<recordId>:<その期の有効期限>`**。
  入金確認をやり直しても同じ期限になるので **二重付与しない**。
  翌期の入金では有効期限が変わるため、**別の期として 1 回だけ**積む。
- 🔴 `MembershipStartedAt` は **初回だけ**書く（更新で起点を動かさない）。
- 🔴 **メールの再送は禁止したまま、membership だけ再実行で回復できる**構造にする。
  入金確認メールが送信済み（`PaymentEmailSent=true`）でも **早期 return しない**。
  早期 return すると「Step 1〜4 は成功したが membership の書き込みだけ失敗した」場合に、
  再実行しても Step 5 へ到達できず、**リワードが永久に欠落する**。
  - 再実行では **メールを送らず、既存列の更新もやり直さない**（membership だけ試す）。
  - 再実行時の入金確認日は **`ExpirationDate − 期間` から復元**する。
    🔴 **現在時刻で代用しない**（数日後の再実行で起点と付与日時が実際の入金日とずれるため）。
  - 冪等キーは有効期限由来なので、初回と再実行で **同じキー**になる＝二重付与しない。

- 🔴 **申込日・登録日は起点にしない。** 支払っていない期間を継続期間に数えない。
- 🔴 **既存データは根拠のあるものだけ backfill する。**
  起点が不明な会員は **空のままにする**（`monthsKnown: false` → 画面は「準備中」）。
  **推測で埋めない。0 か月（＝ Bronze）でも埋めない**
  （長く続けている会員を最低ランクで表示することになる）。
- 実データ上、起点が不明なのは **11 件中 3 件**（`docs/MEMBERSHIP_DATA_MIGRATION.md` §0）。

### 7.7 TBD-10 支払い失敗中の扱い

🔴 **認可（見える範囲）と リワード（貯まる量）を混同しない。** 両者は別々に動く。

| 層 | 支払い失敗中の挙動 |
|---|---|
| **認可 / entitlement** | **現行のまま変更しない。** `invoice.payment_failed` は `Status` を変えるだけで、`PlanType` / `AccessEnabled` は触らない。**アクセスを即時停止しない**（猶予は Stripe の dunning 設定に従う） |
| **継続月数 / リワード付与** | **支払い成功まで保留する。** 失敗した期間には付与しない・月数も増えない |

保留したあとの扱い:

- **再決済が成功したら**、その期間ぶんを **1 回だけ**反映する（100 pt ＋ 1 か月）。
- **同じ期間を二度反映しない**（冪等キーは請求期間の識別子。Stripe の再送でも増えない）。
- **最終的に未払いのまま終了した期間には付与しない**（成功イベントが来ないので自然にそうなる）。

実装の要点:

- 付与は **カレンダーではなく「支払い成功イベント」で駆動する**（`invoice.payment_succeeded`）。
  これにより「失敗した期間は付与されない」「再試行成功で 1 回だけ付く」が構造的に保証される。

🔴 **付与の前提が 1 つでも欠けたら、付与しない（保留する）。**
推測で埋めると、あとから正しい値に直せない誤ったポイントが残るため。

| 前提 | 正本 | 欠けたときの挙動 |
|---|---|---|
| **実際に支払われた金額** | Stripe の **`invoice.amount_paid`** | 🔴 **`total` / `amount_due` で代用しない。付与しない**。🔴 **`amount_paid <= 0` なら付与しない** — トライアル開始時や全額割引の **¥0 請求**でも Stripe は `invoice.payment_succeeded` を出すため（2026-09-05 の Test Clock 実測で 100 pt が誤って付いた）|
| 請求期間の長さ | Stripe の `price.recurring`（`interval` × `interval_count`）| 🔴 **月額へ丸めない。付与しない**（`day` / `week` / 未知の値も同様）。🔴 **`interval_count` が欠けていても 1 で補わない**（実際が四半期・半年払いだった場合に過少なまま確定するため）|
| 支払い成功の時刻 | Stripe の `status_transitions.paid_at` | 🔴 **受信時刻（`Date.now()`）で代用しない。付与しない** |

- 期間は `month`→1か月 / `year`→12か月に `interval_count` を掛けて数える
  （四半期払いなら 3 か月ぶん。月額へ潰さない）。
- **webhook は遅延・再送される。** 受信時刻を付与日時にすると
  「今月の積み上げ」が実際の支払い月とずれるため、必ず Stripe 側の時刻を使う。
- 解約日（90 日の起算）も同じ理由で **イベントの発生時刻**（`event.created`）を使う。
- **継続月数も同じ台帳から数える**（支払い済み期間の累計）。
  月額 1 期 = 1 か月、年払い 1 期 = 12 か月。
- 🔴 **ランク・リワードを認可の判断材料にしない**（§9-4）。逆も同様で、
  `entitlement.js` は台帳を読まない。この分離は静的ガードとテストで固定してある。

| 2 | 🔴 その item が**現在のカタログ**に実在し、600/1,200 pt または 12/24 か月の条件に**本当に該当するか**をサーバー側で再検証 | `validateRedemption()` |
| 3 | 🔴 **client のポイント数・資格・価格を信用しない** | 必要ポイントはカタログから、残高は台帳から数え直す |
| 4 | 🔴 **他会員の残高・住所・交換履歴を参照できない** | すべて session の email で絞って読む |
| 5 | 🔴 二重クリック・再送で**二重減算／二重交換／二重発送依頼にならない** | 申込ごとの冪等キー（`requestId`）→ `RedemptionId` で重複排除 |
| 6 | **記念品はポイントを消費しない** | `costPoints: 0`・台帳へ書かない |
| 7 | 通常交換は既存 **S-2** どおり 12 / 24 か月の月には受け付けない | `isMilestoneMonth()` |

#### 🔴 書く順序（3 段階。片側成功を残さない）

**① `requested` を積む → ② 台帳の減算を冪等に成立させる → ③ 成立したときだけ `approved`。**

静的ガード **G-27** が順序を、**G-29** が「`requested` を発送対象にしない」ことを固定している。

| 失敗した箇所 | 残る状態 | 会員のポイント | 回復 |
|---|---|---|---|
| ① キューへ積めない | 何も残らない | 減らない | 再送でやり直せる |
| ② 減算が失敗 | **`requested`**（発送されない）| 減らない | **再送で減算を引き直し、`approved` へ進む** |
| ③ `approved` にできない | `requested`（発送されない）| 引かれている | 再送で `approved` へ進む（減算は冪等なので二重にならない）|

🔴 **同じ `requestId` の再送で無条件に `already` を返してはいけない。**
`requested` のまま残った申込の減算が**永久に再試行されなくなる**
（2026-09-07 に仕様所有者が指摘。交換行だけ残る片側成功が回復不能だった）。
再送では **状態を見て**、`approved` / `shipped` / `cancelled` なら何もせず、
`requested` なら**減算の有無を確認して引き直す**。

減算の再試行は、台帳に同じ `entryId`（`redemption:<email>:<redemptionId>`）が
既にあるかを見てから行う（**G-30**）。二重減算にはならない。

🟡 **既知の限界**: Airtable にトランザクションが無いため、
**完全同時**の 2 リクエストは「重複なし」を同時に確認しうる（at-least-once）。
二重クリック・再送・遅延再送は冪等キーで防いでいる。
これは `stripe-webhook` の冪等性と同じ水準であり、**運用者が `RewardRedemptions` で重複を確認できる**。

### 7.10 対象決済方式・移行時の引継ぎ・買い切り会員（2026-09-11 確定）

#### 7.10.1 対象決済方式

継続リワード（**会員ランク / 継続月数 / KIリワードポイント / 継続特典・交換品**）の
**主対象は、クレジットカードによる継続決済の会員**である。
これらは **クレジット継続決済の価値**として位置づける。

| 決済方式 | 継続リワード | 契約・閲覧権限 |
|---|---|---|
| **クレジット継続決済** | ✅ **主対象** | 変更なし |
| 銀行振込（月払い・年払い）| 🟡 下記 7.10.2 | 🔴 **変更しない** |
| 買い切り・永久会員 | 🔴 **蓄積の主対象にしない**（7.10.4）| 🔴 **変更しない** |

#### 7.10.2 銀行振込の会員

- 🔴 **現在の契約・閲覧権限を変更しない。**
- **クレジット継続決済へ移行すると継続リワードを受けられる**、という導線にする。
- 🔴 **強制移行はしない。**

🟡 **未確定（TBD-14）**: 銀行振込の期間について、**今後も台帳へ積み続けるか**。

仕様所有者の承認なしに実装しない。

#### 7.10.3 銀行振込 → クレジット継続決済への移行

- **それまでの正当に確認できる継続月数を引き継ぐ。**
- 引き継いだ継続月数に応じて **Bronze / Silver / Gold / Platinum のランクも継続する。**

🔴 **根拠にしてよいのは repo 内の正本データだけ。**

| 根拠 | 使う |
|---|---|
| `RewardLedger` の支払い済み期間 | ✅ |
| `MembershipStartedAt`（＝支払い成功日。§7.6）| ✅ |
| **`CreatedAt`（申込日）** | 🔴 **加入日として使わない** |
| 金額・`PlanType`・推測 | 🔴 使わない |

実装（`resolveTenureMonths()`）:

1. 台帳に支払い済み期間があれば **台帳が正**
2. ＋ **台帳が始まる前の期間**（`MembershipStartedAt` → 最初の台帳エントリ）を足す
3. 起点が保存されていなければ **足さない（0）**。推測で埋めない
4. 台帳も起点も無ければ **`pending`（「準備中」）**。🔴 **0 か月（Bronze）へ倒さない**

🔴 **この計算で継続月数が減ることはない**（移行前 ≦ 移行後）。テストで固定してある。

🟡 **未確定（TBD-16）**: 銀行振込期間について、**移行時に過去分のポイントまで
遡及付与するか**。今回確定したのは **「継続月数」と、それによって決まる「ランク」の引継ぎだけ**。
🔴 **過去ポイントの自動付与は、仕様所有者の承認なしに実装しない。**

#### 7.10.4 買い切り・永久会員

- 🔴 **継続ポイントを貯める仕組みの主対象にしない。**
- 代わりに **専用の称号・バッジ**を与える方向とする。
- 🔴 **既存の永久閲覧権限・契約条件は変更しない。**

実装: `plan_type` が `lifetime` の会員には、**どの経路からも accrual を積まない**。
判定は `rewardScope.js` の `isAccrualForbidden()`、
実際に止めるのは `airtableStore.appendEntry()`（**全付与経路が通る唯一の出口**）。
🔴 **交換（redemption）は止めない**（過去に積んだぶんは使える）。

##### 🔴 意図的な非付与と「書込失敗」を必ず区別する

止めたときに返すのは **`STORE_RESULT.NOT_APPLICABLE`**（仕様どおりの非適用）。
🔴 **`UNAVAILABLE`（＝書けなかった）にしてはいけない。**

`stripe-webhook.js` の `membershipResultFromStore()` は
`applied` / `already` **以外をすべて FAILED** として扱うため、
`UNAVAILABLE` を返すと **webhook が 500 を返し、Stripe が同じイベントを
再送し続ける**（買い切り会員が支払うたびに無限再送になる）。

| store の戻り | webhook の扱い | HTTP |
|---|---|---|
| `applied` / `already` | OK（記録できた）| 200 |
| **`not-applicable`** | **SKIPPED（仕様どおり。再送不要）** | **200** |
| `unavailable` | FAILED（書けなかった。再送させる）| 500 |

##### 🔴 非付与のときは `MembershipStartedAt` も書かない

`recordPaidPeriod()` は台帳へ積んだあと、初回請求なら `saveMembershipStart()` を呼ぶ。
**買い切り会員で付与を止めたのに起点だけ書くと、継続月数の根拠が汚れる**
（起点が空の買い切り会員に、新しい Stripe 初回請求日が「加入日」として入る）。

そこで `not-applicable` のときは **起点の書き込みも行わない**。

🔴 `unavailable`（**本当に書けなかった**）では止めない。
再送で復旧させたいので、起点の書き込みも再試行させる。

同じ理由で `redeemHandler.js` の `settlePoints()` も、
**`applied` / `already` だけ**を「減算が成立した」と見なす
（それ以外を成立扱いにすると、引かれていないのに交換が進む）。

🟡 **未確定（TBD-15）**: **称号名・表示文言**。既存正本に無いため確定させない。
候補（🔴 **どれも未採用。表示に出さない**）:

| 候補 | 意図 |
|---|---|
| `永年会員` | 既存の「永久アクセス」表記に近く、誤解が少ない |
| `フェロー` | ランク（Bronze〜Platinum）と語感が重ならない |
| `オーナーズ` | 買い切り＝保有という含意 |
| `KI パートナー` | 既存の「パートナー」表現と整合 |

🔴 決まるまでは **「準備中」**と表示する（§4 の方針どおり）。

#### 7.10.5 fail-closed 条件

| 状況 | ふるまい |
|---|---|
| 支払い方法の証拠が無い | `PAYMENT_METHOD.UNKNOWN` / `REWARD_SCOPE.UNKNOWN`。**推測しない** |
| `ContractPriceId` と `PaymentMethod` が食い違う | **UNKNOWN**（どちらかへ寄せない）|
| 継続月数の根拠が無い | **`pending`（準備中）**。0 か月へ倒さない |
| `plan_type` が読めない・空・未知 | 🔴 **付与を止めない**（支払い済みの月を落とさないため）|
| 会員レコードが読めない | 🔴 **付与を止めない**（同上）|

🔴 ここでの fail-closed は **「根拠なく付与しない」より「根拠なく既存の付与を止めない」**を
優先する。台帳は**再生成できない**ため、誤って止めると支払い済みの月が永久に欠落する。
逆に、**買い切りだと証拠から分かる**ときは確実に止める。

#### 7.10.6 既存会員を壊さない

- 🔴 **契約・閲覧権限（entitlement / tier）に一切影響させない。**
  `rewardScope.js` は認可のモジュールを import しない（テストで固定）。
- 🔴 **契約価格・`MembershipStartedAt` を勝手に書き換えない。**
- 🔴 **他会員のデータを混ぜない**（台帳・起点は会員ごと。テストで固定）。

## 8. 法令上の前提（保守ラインの内側で運用する）

🔴 **景品表示法・会計処理の最終判断を KI のコード内で断定しない。**
ただし本制度は §7.2 の **保守ライン（1 点 ¥796 以内・全員同一条件）**の内側に収めてあるため、
**運用開始のために確認を待つ必要がある項目は無い**。

### 8.1 保守ラインを維持するために守ること

| # | 守ること | 崩れたときに起きること |
|---|---|---|
| S-1 | 景品 1 点を **¥796 以内**に収める | 取引価額（月額か年額か）の確認が必要になる |
| S-2 | 記念品と通常交換を **同月に重ねない** | 1 か月の景品類が合算され S-1 を超えうる |
| S-3 | **抽選・くじ・先着を入れない**（全員同一条件＝総付を維持） | 一般懸賞となり別の上限が適用される |
| S-4 | リワードを **換金・譲渡・円換算しない** | 前払式支払手段（資金決済法）の議論に入る |

S-1〜S-4 はコード側の静的ガードとテストで固定してある。

### 8.2 判断が必要になったときだけ確認する項目

**いま確認しなくてよい。** 下記の設計変更をしたくなったときに、初めて確認する。

| # | いつ必要になるか | 確認すること |
|---|---|---|
| L-1 | ¥796 を超える景品を出したくなったとき | 継続的役務における「取引価額」の算定（月額か年間合計か） |
| L-2 | 抽選・先着を入れたくなったとき | 一般懸賞の上限（取引価額の20倍・総額は売上予定総額の2%） |
| L-3 | 送料が高い景品を扱うとき | 送料を景品価額に含めるかどうか |
| L-4 | 交換の実運用を始めるとき | `/tokushoho` に継続特典・失効条件・解約時の扱いの表示が要るか（TBD-12 と同時） |
| L-5 | 決算期 | 未使用ポイントの会計処理（引当・契約負債）。**税理士に確認**。§7 の残高上限と 90 日失効により見積りは容易 |

🔴 **失効条件・解約時の扱いは、制度開始と同時に規約へ明記すること。**
後から付けると不利益変更になる。

### 6.3 利用規約（`/terms` 第5条）に書く範囲

会員へ**契約条件**として示すのは、次の 5 点だけである（`/terms` 第5条）。

1. KIリワードは**現金・預金ではなく、換金・払い戻し・第三者への譲渡ができない**（§3.3 / §8.1 S-4）
2. **お支払いが成功した期間**に対して **1 か月あたり 100 pt** を付与する（§7.1 / §7.7）
3. **ご契約が続いている間は失効しない**（§7.1 TBD-6）
4. **解約日から 90 日**で失効する（§7.1 TBD-6 / TBD-7）
5. **90 日以内の再加入**でポイントと**継続価格ロック**が戻る（§7.1 TBD-7 / TBD-8）
