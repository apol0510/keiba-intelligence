# AI作業ルール

## 🚨 最重要：作業開始時の必須行動 🚨

### 作業開始時に必ず明示すること

```
【今回の目的】
...

【変更対象ファイル】
...

【完了条件】
...
```

### 作業途中の報告形式

```
【確認したこと】
...

【判明したこと】
...

【次にやること】
...
```

### 完了時の報告内容

1. 変更内容の要約
2. 修正前後の比較（数値修正の場合は必須）
3. git diffの要約
4. 確認方法または確認URL

---

## ⚠️ AI作業の絶対禁止事項 ⚠️

### 1. 推測でコードを書かない

- ❌ **ファイルを読まずにコード修正しない**
- ❌ **「多分こうだろう」で実装しない**
- ✅ Read toolで該当ファイルを読んでから修正
- ✅ 実データを確認してから結論を出す

### 2. 指示されていない変更を勝手に広げない

- ❌ **「ついでに」の改善を勝手に実施しない**
- ❌ **依頼範囲外のリファクタリングをしない**
- ✅ 依頼された変更のみ実施
- ✅ 追加提案は「提案」として明示

### 3. 完了条件を満たさない完了宣言の禁止

- ❌ **テスト未実施で「完了」と宣言しない**
- ❌ **実データ確認せずに「修正しました」と言わない**
- ✅ 完了条件を全て満たしてから完了宣言
- ✅ 確認方法または確認URLを提示

### 4. 数値修正は修正前後の比較を必ず出す

- ❌ **「修正しました」だけの報告**
- ✅ **修正前: 33% → 修正後: 58.3%** の形式で報告
- ✅ 全対象日付の修正前後を表形式で提示

### 5. commit前にgit diffを確認する

- ❌ **変更内容を確認せずにcommit**
- ✅ `git diff` で変更内容を確認してからcommit
- ✅ 削除されたファイル・追加されたファイルを明示
- ✅ 予期しない変更がないか確認

### 6. 本番反映前に確認方法を示す

- ❌ **「デプロイしました」だけの報告**
- ✅ 確認URL、確認手順を明示
- ✅ 本番で期待通り動作するか検証方法を提示

## 📊 データ修正時の必須確認事項 📊

### archiveResults.json修正時

1. **修正前の値を確認**
   - Read toolでarchiveResults.jsonを読む
   - 該当日付の現在値を記録

2. **修正処理実行**
   - importResults.js等のスクリプト実行
   - エラーがないか確認

3. **修正後の値を確認**
   - 再度Read toolで確認
   - 修正前後の比較を表形式で提示

4. **検証実行**
   - `npm run validate:archive` 実行
   - フォーマット検証が通ることを確認

5. **git diff確認**
   - 予期しない変更がないか確認
   - 削除行数・追加行数を確認

### 数値集計時

- ✅ 月間統計の再計算を実施
- ✅ 的中率・回収率の整合性確認
- ✅ 極端な数値（300%超など）の理由を説明

## 🛡️ 旧フォーマット混入防止ルール 🛡️

### 禁止キー（旧フォーマット）

以下のキーは**絶対に使用禁止**：
- `raceResults`
- `honmeiHit`
- `umatanHit`
- `sanrenpukuHit`

### 新フォーマット（正）

- `races`
- `isHit`
- `hitLines`

### 検証義務

- archiveResults.json修正後は必ず `npm run validate:archive` 実行
- エラーが出たら即座に修正
- 旧フォーマット混入は**エラー扱い**

詳細は [`docs/DATA_FORMAT.md`](./DATA_FORMAT.md) 参照。

## 🔍 結果システム変更時の参照義務 🔍

結果ページ・アーカイブ・importResults系スクリプトを変更する場合：

### 必ず参照するドキュメント

1. [`docs/RESULTS_SYSTEM_ARCHITECTURE.md`](./RESULTS_SYSTEM_ARCHITECTURE.md)
   - 結果システム全体設計
   - JRA / 南関の違い
   - importResults系スクリプトの役割

2. [`docs/MULTI_VENUE_CHECK.md`](./MULTI_VENUE_CHECK.md)
   - 複数会場同日開催の注意点
   - venue / venues の扱い
   - マッチングロジックの違い

3. [`docs/DATA_FORMAT.md`](./DATA_FORMAT.md)
   - archiveResults.jsonの正式フォーマット
   - 禁止する旧フォーマット

### 参照せずに変更した場合のリスク

- ❌ 2会場同時開催時に片方の会場が消える
- ❌ 的中判定が誤る（的中率25%など）
- ❌ 旧フォーマット混入でビルド失敗

## 🎯 作業完了の基準 🎯

### 以下を全て満たした場合のみ「完了」

1. **目的達成**
   - 依頼された変更が完了している
   - 意図しない変更が含まれていない

2. **実データ確認済み**
   - Read toolで修正後のデータを確認
   - 数値修正の場合は修正前後の比較を提示

3. **検証済み**
   - npm run validate:archive（データ修正の場合）
   - npm run build（ビルドエラーなし）

4. **git diff確認済み**
   - 予期しない変更がないか確認
   - 削除・追加行数を明示

5. **確認方法提示済み**
   - 本番URL、確認手順を明示
   - 期待される動作を説明

## ❌ 禁止事項まとめ ❌

| 禁止事項 | 理由 |
|---------|------|
| ファイルを読まずに修正 | 現在の実装を知らないまま変更すると破壊的変更になる |
| 依頼範囲外の変更 | 意図しない副作用を生む |
| 完了条件未達で完了宣言 | 実際には完了していないのに完了と報告すると信頼を失う |
| 数値修正の比較なし報告 | 修正が正しいか検証できない |
| git diff未確認でcommit | 予期しない変更がコミットされる |
| 確認方法なしで本番反映 | 本番で問題が起きても気づけない |
| 旧フォーマット混入 | ビルド失敗・的中率誤表示 |

---

## ✅ 推奨行動まとめ ✅

| 推奨行動 | 効果 |
|---------|------|
| 作業開始時に目的・対象・完了条件を明示 | 作業範囲が明確になる |
| Read toolで実データ確認 | 現状を正しく把握できる |
| 修正前後の比較を提示 | 修正が正しいか検証できる |
| npm run validate:archive 実行 | 旧フォーマット混入を防止 |
| git diff確認後commit | 予期しない変更を防止 |
| 確認方法・URLを提示 | 本番で期待通り動作するか検証できる |
