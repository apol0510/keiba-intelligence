### 1.1 期間中の成績では説明できない

同期間の公開成績（archiveResults / archiveResultsJra、表示上の回収率）は、解約者と継続者で差がない。

| 区分 | 的中率 | 表示回収率 |

「当たらない月に辞める」（decisions.md 2026-09 の想定）ではない。

### 1.2 🔴 主因の仮説: 公開成績と会員体験の乖離（検証済みの事実＋推論）

**事実**（コードと archive で再現。2026-09-01〜10-05・582 レース）:

- 回収率は **1 レース 5 点（500 円）** を投資として計算している（`importResults*.js` の `BET_POINTS_PER_RACE = 5`）。
- 会員の買い目パネルは同じ F3 判定の組み合わせを **約 16 点**表示し、見出しは「推奨 6〜12 点」。どの点を買うかは示していない。
- 的中は 16 点を全部買ったときにだけ成立する。表示どおり全点を買った場合の回収率は **約 79%**（南関 72% / JRA 85%）で、公開値 **234%** の約 1/3。
- `/pricing` の FAQ は「1レースあたりの投資は5点固定」。トップの「回収率（通算）」に注記はない（注記は結果・アーカイブページのみ）。
- この分離は `BET_POINT_LOGIC.md` / `decisions.md` 2026-07-01・07-02 で意図的に採用されており、再検討条件が「回収率の投資基準を表示点数に合わせること」だった。

**推論**（データで断定はできない）: C の自由記述「思っている内容と大きな格差」、加入直後（14 時間・2 日）の解約、
「高すぎる」「不要になった」は、**公開成績を見て加入 → 実際の買い目点数と費用感が想定と違う**、という体験と整合する。

🔴 公開成績・料金ページの文言をどう直すかは **事業判断（顧客向け文言）** なので、本件では変更しない（§4）。

### 1.3 副次要因

- **ログインの手間**: セッションは 7 日で切れ、magic link を再要求する（D は 7 日ごとに再ログイン、B は短時間に連続発行）。
- **計測なし**: マイページ・ポータル・解約・取り消しの GA4 イベントが無く、離脱点を数えられなかった。
- **解約予約中であることがマイページに出ない**: K3 はポータルの奥の「更新」で自力で取り消した。

## 2. 継続導線の設計（本 PR で実装）

原則: 🔴 **いつでも解約できることは変えない**。🔴 **値引きは入れない**（原因判明前・ユーザー指示）。
🔴 煽り・罪悪感・期限圧の文言を使わない。🔴 成績（回収率・的中率）を継続理由に使わない（§1.2 が未決のため）。

| 要素 | 内容 |
|---|---|
| 解約予約中の表示 | プランカードに「解約のお手続きを受け付けています」、終了日時と残り日数、終了すると使えなくなる機能（AI指数の数値 / AI結論 / 馬単の買い目）、確定しているときだけ KIリワード残高と契約価格が 90 日以内の再開で戻る旨 |
| 取り消し | 「解約予約を取り消して継続する」1 クリック。取り消さなくても期間末まで追加料金なしで使える旨を併記 |
| 継続中 | 「次回のお支払い: YYYY年M月D日」 |
| お支払い欄 | 従来どおり（「お支払い方法の変更・プラン変更・解約は、お支払い管理ページから行えます。」＋ポータルボタン）。🔴 解約を想起させる追加文言は出さない（2026-10-06 MK 決定） |

### 2.1 実装

- `netlify/functions/stripe-subscription.js`: POST `{action:'status'|'resume'}`。ログイン必須・顧客はセッション email で検索（`stripe-portal.js` と同じ契約）。
  本文の subscription ID 等は受け取らない。返すのは状態と日付だけ。
- `src/lib/billing/subscriptionState.js`: 解約予約の判定（`cancel_at` / `cancel_at_period_end` の両方）、要約、取り消しパラメータ。
- 取り消しは `subscriptions.update(id, { cancel_at: '' })`（旧来の予約は `cancel_at_period_end: false`）。
  予約が無ければ書き込まない。idempotency key は `ki-resume-<sub>-<cancel_at>`。更新後に予約が残っていれば 502。
- Airtable の会員状態は従来どおり webhook（`customer.subscription.updated`）が反映する。新しい書き込み経路は作らない。

### 2.2 検証

- 単体・関数: `stripeSubscription.test.mjs`（19 件。認可 / 他人の契約を操作できない / 冪等 / 予約解除以外を送らない / 文言ガード / GA4 に PII なし）。`npm run test:stripe` と `npm run build` に組み込み。
- Stripe API の実挙動: Stripe サンドボックス（API 2026-08-26.dahlia・flexible 請求）で
  「期間末キャンセル予約 → `cancel_at=""` → 予約解除・次回請求 ¥3,980 復帰」を確認。テスト顧客は削除済み。
- ブラウザ: localhost で premium セッション＋関数応答の差し替えにより、予約中表示 → 取り消し → 次回支払日表示・完了メッセージ・狭幅レイアウトを確認。
- 本番反映後: `.github/workflows/post-deploy-billing-smoke.yml` が main への push（課金・マイページの変更のみ）で起動し、
  本番反映を最大 15 分待ってから未ログインの 8 項目（401 / 405 / 400 / 200）を確かめる。失敗は failure(red)。secrets 不要・本番データに触れない。
